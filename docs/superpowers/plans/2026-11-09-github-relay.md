# Временный GitHub-прокси внутри установщика

Пользователь подтвердил рабочий SSH-прокси на своём проде и потребовал один
установщик без двух терминалов и ручного туннеля. Реализация выполняется сразу
по уже согласованной схеме: прямое скачивание, затем предложение прокси и ввод
общего пароля, автоматическое закрытие соединения. Отдельное подтверждение
дизайна не требуется: пользователь явно просит закончить работу.

## Решения

- Встраиваем в install.sh, не добавляем обязательный вспомогательный файл.
  Сам install.sh при заблокированном GitHub один раз переносится на сервер.
- SSH 31.130.132.194:2222, пользователь relay. ED25519 закреплён по отпечатку
  SHA256:DXlwUOYrx9brdSSIW72VQL4CGvS/5G8onnqri6LBflg из установки на проде.
  Сканирование ключа проверяется до передачи пароля; проверка SSH/TLS/GPG
  не отключается. Пароль читает сам SSH из терминала, без argv/env/файлов.
- with_download_context владеет временным каталогом и ControlMaster;
  вложенные setup_auto_update/run_auto_update используют общие файлы состояния.
  Один вход на операцию. Конец операции/ошибка/HUP/INT/TERM закрывают туннель.
- download_transport вызывается из safe_download и bootstrap_python.
  Только HTTPS GitHub/raw/release-assets могут предложить резервный маршрут;
  localhost, Remi, пользовательские источники и диагностический Python-аудит
  не получают глобальных proxy-переменных. SOCKS передаёт DNS через прод.
- Автоматический режим без терминала и --unattended не спрашивают пароль.
  Ошибка HTTP 404/локальной записи не считается блокировкой GitHub.
- Сохраняем существующие проверки сервера, подписи, снимка и разрешения
  установки PHP. На пользовательских серверах ничего сами не выполняем.

## Работа и проверки

- [x] Новый поведенческий тест: зафиксировать отказ до реализации.
- [x] Общий транспорт, закреплённый ключ, локальный случайный SOCKS-порт,
  повторное использование состояния и очистка без вмешательства в чужие SSH.
- [x] Вызовы из основных CLI-операций и bootstrap, версия rc12, документация.
- [x] Прямой путь, блокировка, отказ/нет терминала, 404, чужой хост,
  неверный ключ/пароль, несколько скачиваний в разных subshell, сигналы.
- [x] Реальный локальный SSH-тест пароля, фонового соединения и очистки.
- [x] Регрессии существующего меню, настройки, подписанных комплектов обеих веток.
- [x] Независимая проверка; исправить найденное; передать готовый install.sh
  и однозначную команду запуска. Не представлять локальный файл как уже
  опубликованный в main, если публикации не было.

## Особое внимание

Не оставить SSH с дескриптором блокировки/лога; не потерять состояние между
двумя subshell; не перезаписать существующие EXIT-trap; не отправить пароль
чужому ключу; не пустить локальный health-check через прод; сохранить исходный
код завершения при очистке. Рабочая ветка codex/github-relay-fallback.

## Результат

09.11.2026: 21 транспортная проверка (12.055 с) и 3 проверки настоящего
SSH/SOCKS (2.285 с) прошли. Проверены шестисимвольный тестовый пароль,
скачивание ключа (1155 байт) и манифеста выпуска (4641 байт), повторное
использование туннеля и завершение фонового SSH. Пройдены прежние наборы
CentOS 7 и Python: publisher, client 8.2/8.3, environment, 100 подтверждений,
menu, next-actions, report-menu, setup, managed-integration и 59 branch-проверок.
Проверяемый install.sh SHA256:
cb5f6c6c0cc0e2433cfb5bf5a0466208dd801e5b7ab5ed1ec3880b1282fa7b90.

Независимое ревью исправило позднее переключение при перенаправленном stdin
и сохранило прежние retry/timeout для источников вне GitHub. Bash 4.2,
параметры curl 7.29, ss CentOS 7 и git diff --check проверены. ShellCheck
на полном историческом скрипте продолжает показывать прежние предупреждения
SC1007/SC2174/SC2190 вне изменённого транспорта; чистый ShellCheck не заявляется.
На пользовательских серверах новый установщик не запускался; реальные тесты
работали с одноразовым локальным sshd. После успешного обновления пользовательского
сервера владелец отдельно поручил сделать коммит и отправить его прямо в main.
