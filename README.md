# Bitrix PHP 8.2 Updater

Русскоязычный мастер для администраторов старых серверов BitrixEnv 7.
Проверяет сервер, показывает последовательность перехода на PHP 8.2
и устанавливает подготовленный патч PHP 8.2.35 с проверками и откатом.

## Поддерживаемая установка

| Компонент | Требование |
|---|---|
| ОС | CentOS 7, x86_64 |
| Окружение | BitrixEnv со штатной конфигурацией Apache |
| Исходный PHP | RPM-пакеты PHP 8.2.0–8.2.34 |
| Веб-PHP | Apache prefork/mod_php |
| Цель | PHP 8.2.35 |
| Восстановление | Точные старые RPM и проверенный снимок сервера |

Для автоматической загрузки первый выпуск содержит старые пакеты
**PHP 8.2.20-1.el7.remi, x86_64, без epoch**. Для другого выпуска 8.2.x
нужно сначала добавить его точные оригинальные RPM в подписанный архив.
Диапазон в таблице описывает возможности установщика; наличие всех старых
пакетов конкретного сервера проверяется отдельно перед установкой.

При PHP 8.2.35 мастер проверяет установленную версию и сайт.
Для PHP-FPM, SCL, других ОС и нестандартного состава пакетов смотрите результат диагностики.
Версии PHP 5.x, 7.x, 8.0 и 8.1 сначала переводят на 8.2 по маршруту из плана.

Выпуск пилотный. Перед применением на рабочем сервере пройдите обновление и откат на его клоне.
CentOS 7 снята с поддержки. Этот проект предназначен для временного обновления PHP
при подготовке дальнейшей миграции окружения.

## Начало работы

Скачайте скрипт в отдельный каталог и проверьте версию.

~~~bash
curl --fail --location --output install.sh \
  https://raw.githubusercontent.com/vitikevich-landau/bitrix-php82-updater/main/install.sh
bash install.sh --version
bash install.sh --check
~~~

Для управления через меню достаточно запустить файл без флагов.

~~~bash
bash install.sh
~~~

Главное меню открывает разделы проверок, подготовки и обновления, отката и состояния.
В разделе проверок доступны быстрый чек, план действий, полный аудит и проверка сайта.
Пункты установки требуют root. Цветовые статусы работают в терминале.

## Одна команда обновления

На каждом сервере один раз подготовьте закрытый веб-тест по подробной инструкции.
Он должен возвращать фактическую версию PHP именно сайта и проверять нужные расширения.
Затем запустите настройку от root.

~~~bash
bash install.sh --setup-update
~~~

Настройка проверит URL сайта, скачает публичный ключ проекта, сверит закреплённую
контрольную сумму ключа и сохранит параметры в /etc/bitrix-php-update.conf.
Источник по умолчанию — подписанный выпуск php-8.2.35-el7-r1 в GitHub Releases.

После настройки обновление запускается одной командой или через раздел обновления в меню.

~~~bash
bash install.sh --auto-update
~~~

Мастер определяет установленные RPM, проверяет подписанные каталоги выпуска,
скачивает точный комплект для отката и новые пакеты, проверяет транзакцию и сайт,
запрашивает подтверждение проверенного снимка и установки, затем обновляет PHP.
Перед перезапуском Apache проверяется конфигурация, после него — PHP и закрытый веб-тест.

Для заранее подготовленного задания доступны явные подтверждения.

~~~bash
bash install.sh --auto-update --unattended --backup-verified
~~~

Параметр --backup-verified означает, что администратор уже проверил актуальный снимок
или резервную копию. Подтверждение передаётся при каждом таком запуске.

Если в выпуске отсутствует точный старый RPM, мастер укажет недостающую запись
и завершит подготовку до установки. Для этого сервера владелец выпуска должен
добавить оригинальный пакет в подписанный архив. Набор файлов установленного PHP
и база RPM сами по себе не заменяют исходный RPM.

Адрес проверки сайта и параметры источника описаны в подробной инструкции.
Для отдельной конфигурации можно передать --config /root/client-update.conf.
Серверу нужен HTTPS-доступ к GitHub и его узлам загрузки файлов.

Выпуск содержит пакеты PHP. Системные библиотеки должны уже удовлетворять
их зависимостям: автоматическая команда не меняет репозитории и не обновляет
остальную ОС. Если библиотек не хватает, предварительная проверка RPM
выведет список недостающих зависимостей и остановит обновление.

## Если PHP ниже 8.2

~~~bash
bash install.sh --check
bash install.sh --plan
~~~

Следуйте маршруту для найденного выпуска BitrixEnv. Администратор запускает
штатное меню окружения от root командой bash /root/menu.sh.

Для PHP 7.4 переходы выполняются отдельными этапами 7.4 → 8.0 → 8.1 → 8.2.
После каждой завершённой фоновой задачи проверяют сайт, модули и доступные обновления.
Для PHP 5.x и ранних 7.x промежуточные версии подбираются по совместимости сайта.
После достижения 8.2 повторите чек.

## Откат

Сохраните ID исходного обновления из вывода мастера.

~~~bash
bash install.sh --status
bash install.sh --rollback --session YYYYMMDDTHHMMSSZ-PID
~~~

Мастер использует подписанные старые RPM из сохранённой сессии.
При повторном запуске после прерванной пакетной транзакции он восстанавливает
весь нужный комплект и повторяет проверки. База данных и файлы сайта
восстанавливаются из вашей резервной копии при необходимости.

## Подготовка выпуска владельцем проекта

Эту работу выполняют на доверенной сборочной машине. Один выпуск можно
использовать у клиентов с подходящим профилем и доступным точным набором для отката.

1. Соберите новые RPM на отдельном клоне через --build --builder.
2. Соберите точные оригинальные старые RPM из доверенных источников.
3. Подготовьте RSA-ключ подписи на доверенной машине.
4. Создайте подписанный комплект одной командой.

~~~bash
bash install.sh --prepare-release \
  --new-rpm-dir /srv/php-update/new \
  --old-rpm-dir /srv/php-update/old \
  --signer FULL_RSA_FINGERPRINT \
  --output /srv/php-update/release
~~~

Команда проверяет метаданные RPM, создаёт NEW-SHA256SUMS и OLD-SHA256SUMS,
подписывает оба манифеста и экспортирует release-keyring.gpg.
Готовый каталог появляется после успешного завершения проверок.
Закрытый ключ остаётся на машине подписи.

Загрузите RPM, оба манифеста и их .asc-подписи в GitHub Release с согласованным тегом.
Публичный ключ для клиентов находится также в репозитории и закреплён хешем в скрипте.
При смене ключа требуется согласованное обновление скрипта и доверия у клиентов.

Старые RPM адресуются по хешу точной записи NEVRA. Это позволяет отличать
разные epoch, версии и release одного пакета. Подлинность файлов проверяется
по подписанному манифесту, а точное соответствие — по метаданным самого RPM.
