# Bitrix PHP Updater 8.2/8.3

Русскоязычный мастер для администраторов старых серверов BitrixEnv 7.
Проверяет сервер, показывает последовательность перехода старого PHP на 8.2
и обновляет уже установленную ветку: PHP 8.2 до 8.2.35 или PHP 8.3 до 8.3.36.
Ветку выбирает автоматически; переходов между ветками и понижений версии нет.

## Поддерживаемая установка

| Компонент | Требование |
|---|---|
| ОС | CentOS 7, x86_64 |
| Окружение | BitrixEnv 7 со штатной конфигурацией Apache |
| Исходный PHP | RPM-пакеты PHP 8.2.0–8.2.34 или 8.3.0–8.3.35 |
| Веб-PHP | Apache prefork/mod_php |
| Цель | PHP 8.2 → 8.2.35; PHP 8.3 → 8.3.36 |
| Восстановление | Точные старые RPM и проверенный снимок сервера |

Для автоматической загрузки предусмотрены отдельные подписанные выпуски:

| Ветка | Целевой выпуск | Исходные пакеты в архиве отката |
|---|---|---|
| 8.2 | [php-8.2.35-el7-r1](https://github.com/vitikevich-landau/bitrix-php-updater/releases/tag/php-8.2.35-el7-r1) | 8.2.20-1.el7.remi, x86_64, без epoch |
| 8.3 | [php-8.3.36-el7-r1](https://github.com/vitikevich-landau/bitrix-php-updater/releases/tag/php-8.3.36-el7-r1) | 8.3.8-1.el7.remi, x86_64, без epoch |

Для другого исходного выпуска нужно сначала добавить его точные оригинальные
RPM в подписанный архив своей ветки. Существующий архив PHP 8.2 не меняется.
Диапазон в таблице описывает возможности установщика; наличие всех старых
пакетов конкретного сервера проверяется отдельно перед установкой.

RPM проекта собираются из Remi SRPM с адаптацией к CentOS 7 и OpenSSL 1.0.2.
Опубликованные RPM PHP 8.2 имеют выпуск `8.2.35-1.el7.1`.
Исходный RPM, spec, патч и результаты проверки публикуются вместе с комплектом.
Выпуск PHP 8.3 содержит RPM 8.3.36-1.el7.1. Сборка, зависимости и
обновление с откатом проверены; подробности — в разделе проверки rc10 ниже.

При PHP 8.2.35 или 8.3.36 мастер проверяет установленную версию и сайт.
Более новый патч той же ветки не понижается.
Для PHP-FPM, SCL, других ОС и нестандартного состава пакетов смотрите результат диагностики.
Версии PHP 5.x, 7.x, 8.0 и 8.1 сначала переводят на 8.2 по маршруту из плана.
PHP 8.4 и выше, а также BitrixEnv 9 этот мастер не обновляет; маршрут на 8.2
к ним не применяется. BitrixEnv 7.5.5 — последний выпуск ветки 7 с поддержкой
PHP 8.3. Сведения о поддержке PHP по выпускам окружения приведены
в [официальной истории BitrixEnv](https://www.1c-bitrix.ru/download/vmbitrix.php).

Выпуск пилотный. Перед применением на рабочем сервере пройдите обновление и откат на его клоне.
CentOS 7 снята с поддержки. Этот проект предназначен для временного обновления PHP
при подготовке дальнейшей миграции окружения.
Наличие целевого патча не означает отсутствия уязвимостей всего сервера.
Обновления безопасности PHP 8.2 завершаются 31.12.2026, PHP 8.3 — 31.12.2027;
актуальный статус ветки и поддержку ОС проверяют отдельно.

## Начало работы

Скачайте скрипт в отдельный каталог и проверьте версию.

~~~bash
curl --fail --location --output install.sh \
  https://raw.githubusercontent.com/vitikevich-landau/bitrix-php-updater/main/install.sh
bash install.sh --version
bash install.sh --check
~~~

Для управления через меню достаточно запустить файл без флагов.

~~~bash
bash install.sh
~~~

Главное меню открывает разделы проверок, подготовки и обновления, отката и состояния.
В разделе проверок доступны быстрый чек, план действий, полный аудит и проверка сайта.
Пункты установки и временная проверка сайта требуют root. Цветовые статусы работают в терминале.

Во всех подтверждениях принимаются `y`, `yes`, `да` для согласия и `n`, `no`,
`нет` для отказа, без учёта регистра. Enter означает отказ. При опечатке мастер
повторит вопрос. Прежние полные фразы, например `СНИМОК ПРОВЕРЕН` или
`ОБНОВИТЬ PHP`, также принимаются в любом регистре. Подтверждение проверенного
снимка и подтверждение установки запрашиваются отдельно.

Для отдельной проверки веб-PHP запустите:

~~~bash
bash install.sh --check-site
~~~

Мастер найдёт сайты в активной конфигурации Apache. Единственный сайт выберет сам,
при нескольких предложит выбор. Для явного выбора передайте `--site site.ru`
или абсолютный DocumentRoot. Без терминала неоднозначный выбор завершится ошибкой.
`--check` остаётся диагностикой без создания теста; `--check-site` кратковременно
создаёт PHP-файл в каталоге выбранного сайта и удаляет его после проверки.

## Одна команда обновления

На поддерживаемом PHP 8.2.x или 8.3.x запустите от root одну команду
или выберите автоматическое обновление в меню. Готовить PHP-файл и URL не нужно.

~~~bash
bash install.sh --auto-update
~~~

Для PHP 8.2 команда выберет 8.2.35, для PHP 8.3 — 8.3.36.
Параметр выбора ветки на клиентском сервере не нужен.

При первом запуске мастер сам выберет сайт, выполнит временную веб-проверку,
скачает публичный ключ проекта и сверит закреплённую контрольную сумму.
Параметры сохраняются в `/etc/bitrix-php-update.conf` с `HEALTH_URL=auto`
и описанием выбранного сайта. Источник по умолчанию — подписанный выпуск
php-8.2.35-el7-r1 или php-8.3.36-el7-r1 своей ветки в GitHub Releases.
Необязательная команда `--setup-update`
позволяет выполнить или повторить эту настройку отдельно.
В терминале повторная настройка снова предлагает выбрать сайт; без терминала
используется сохранённый выбор, если не передан `--site`.

Для выбора сайта при настройке или обновлении используйте `--site`:

~~~bash
bash install.sh --auto-update --site site.ru
bash install.sh --setup-update --site /home/bitrix/www
~~~

Мастер определяет установленные RPM, проверяет подписанные каталоги выпуска,
скачивает точный комплект для отката и новые пакеты, проверяет транзакцию и сайт,
запрашивает подтверждение проверенного снимка и установки, затем обновляет PHP.
Перед перезапуском Apache проверяется конфигурация, после него — CLI и веб-PHP.
Каждая веб-проверка создаёт новый временный тест и сразу удаляет его;
во время загрузки RPM и ожидания подтверждений тест на сайте не остаётся.

Для заранее подготовленного задания доступны явные подтверждения.

~~~bash
bash install.sh --auto-update --unattended --backup-verified
~~~

Параметр --backup-verified означает, что администратор уже проверил актуальный снимок
или резервную копию. Подтверждение передаётся при каждом таком запуске.
Если конфигурации ещё нет и найдено несколько сайтов, добавьте `--site site.ru`.

Если в выпуске отсутствует точный старый RPM, мастер укажет недостающую запись
и завершит подготовку до установки. Для этого сервера владелец выпуска должен
добавить оригинальный пакет в подписанный архив. Набор файлов установленного PHP
и база RPM сами по себе не заменяют исходный RPM.

Выбор сайта и параметры источника описаны в подробной инструкции.
Для отдельной конфигурации можно передать --config /root/client-update.conf.
Указанный явно файл должен уже существовать. Прежние конфигурации с HTTP(S)-URL
и режим `--url` для самостоятельно подготовленного теста продолжают работать.
Сохранённый штатный адрес выпуска проекта, включая прежнее имя репозитория
`bitrix-php82-updater`, сопоставляется с установленной веткой. Произвольный
адрес `SOURCE` остаётся неизменным; пакеты другой ветки блокируются до установки.
Серверу нужен HTTPS-доступ к GitHub и его узлам загрузки файлов.

Выпуск содержит пакеты PHP. Системные библиотеки должны уже удовлетворять
их зависимостям: автоматическая команда не меняет репозитории и не обновляет
остальную ОС. Если библиотек не хватает, предварительная проверка RPM
выведет список недостающих зависимостей и остановит обновление.
По сравнению с официальным комплектом 8.2.20 у CLI-сборки 8.2.35 добавлена
зависимость от стандартной библиотеки `libgcc`. Она уже присутствовала
на проверенном стенде. Остальные изменения Requires касаются внутренних
версий пакетов PHP. Это результат проверки ветки 8.2, а не подтверждение
зависимостей нового комплекта 8.3.

## Что проверяет временный тест

Файл создаётся в отдельном каталоге root под DocumentRoot выбранного Apache vhost.
Запрос выполняется на loopback с именем и портом этого сайта. Тест требует
случайный секретный HTTP-заголовок, локальный адрес отправителя и короткий срок
действия. Секрет не передаётся в URL и не записывается в PHP-код; в нём хранится хеш.
Запросы без секрета до и после успешной проверки должны получить отказ.
Мастер проверяет версию PHP, SAPI `apache2handler`, `mbstring` и `mysqli`.

При обычном завершении, ошибке и обрабатываемых сигналах прерывания файлы удаляются.
После SIGKILL или отключения питания срок действия ограничивает доступ;
следующая автоматическая веб-проверка попытается безопасно удалить остатки
по защищённой записи. Изменённые файлы, неполные записи и артефакты,
принадлежность которых не удалось подтвердить, сохраняются с сообщением
для проверки администратором.

Настройки Apache/nginx для теста не меняются и службы не перезапускаются.
Проверка не загружает приложение и не подтверждает работу nginx, БД,
админки Битрикса, форм и фоновых заданий: их проверяют отдельно на клоне.

## Если PHP ниже 8.2

~~~bash
bash install.sh --check
bash install.sh --plan
~~~

Следуйте маршруту для найденного выпуска BitrixEnv. Администратор запускает
штатное меню окружения от root командой bash /root/menu.sh.

Для PHP 7.4 переходы выполняются отдельными этапами 7.4 → 8.0 → 8.1 → 8.2.
После каждой завершённой фоновой задачи проверяют сайт, модули и доступные обновления.
Для PHP 5.x и ранних 7.x промежуточные версии подбираются по совместимости сайта.
После достижения 8.2 повторите чек.

## Откат

Сохраните ID исходного обновления из вывода мастера.

~~~bash
bash install.sh --status
bash install.sh --rollback --session YYYYMMDDTHHMMSSZ-PID
~~~

Мастер использует подписанные старые RPM из сохранённой сессии.
Ветка берётся из исходной версии в сессии, в том числе при неработающем PHP.
Прежние сессии PHP 8.2 поддерживаются; пакеты другой ветки не допускаются.
Для автоматической проверки он сохраняет описание сайта, а при откате создаёт
свежий тест после восстановления RPM и перезапуска Apache. Рабочий PHP
и успешная проверка конфигурации Apache до восстановления для этого не нужны.
Сессии прежних версий продолжают использовать сохранённый закрытый URL;
явный `--url URL` позволяет задать другой существующий маршрут проверки.
При повторном запуске после прерванной пакетной транзакции он восстанавливает
весь нужный комплект и повторяет проверки. База данных и файлы сайта
восстанавливаются из вашей резервной копии при необходимости.

## Подготовка выпуска владельцем проекта

Эту работу выполняют на доверенной сборочной машине. Один выпуск можно
использовать у клиентов с подходящим профилем и доступным точным набором для отката.

1. Соберите новые RPM на отдельной сборочной машине через `--build --builder`.
   Для PHP 8.3 добавьте `--branch 8.3`.
2. Соберите точные оригинальные старые RPM из доверенных источников.
3. Подготовьте RSA-ключ подписи на доверенной машине.
4. Создайте подписанный комплект одной командой.

~~~bash
bash install.sh --prepare-release \
  --new-rpm-dir /srv/php-update/new \
  --old-rpm-dir /srv/php-update/old \
  --signer FULL_RSA_FINGERPRINT \
  --output /srv/php-update/release
~~~

Без `--branch` сборка и подготовка выпуска сохраняют прежний выбор PHP 8.2.
Для отдельного выпуска PHP 8.3 используйте новые каталоги:

~~~bash
bash install.sh --build --builder --branch 8.3
bash install.sh --prepare-release --branch 8.3 \
  --new-rpm-dir /srv/php83-update/new \
  --old-rpm-dir /srv/php83-update/old \
  --signer FULL_RSA_FINGERPRINT \
  --output /srv/php83-update/release
~~~

Параметр `--branch` предназначен только для `--build` и `--prepare-release`.
Каждый подписанный комплект содержит пакеты одной ветки.

Команда проверяет метаданные RPM, создаёт NEW-SHA256SUMS и OLD-SHA256SUMS,
подписывает оба манифеста и экспортирует release-keyring.gpg.
Готовый каталог появляется после успешного завершения проверок.
Закрытый ключ остаётся на машине подписи.

Загрузите RPM, оба манифеста и их .asc-подписи в GitHub Release с согласованным тегом.
Публичный ключ для клиентов находится также в репозитории и закреплён хешем в скрипте.
При смене ключа требуется согласованное обновление скрипта и доверия у клиентов.

Старые RPM адресуются по хешу точной записи NEVRA. Это позволяет отличать
разные epoch, версии и release одного пакета. Подлинность файлов проверяется
по подписанному манифесту, а точное соответствие — по метаданным самого RPM.

## Проверка первого комплекта RPM PHP 8.2

Следующие результаты относятся к прежнему прогону первого бинарного комплекта
и установщика rc8. Они не заменяют проверку временных тестов rc9 на клоне.

На изолированном CentOS 7 выполнены установка 32 новых RPM и возврат
всего исходного набора. Автоматическая команда отдельно прошла обновление
31 основного пакета без PHP-FPM, повторный запуск, откат и повторный откат.
Apache/mod_php и CLI прошли функциональные пробы; ZIP, APCu, Memcached,
igbinary и msgpack сохранили работоспособность.

Служба Apache в контейнере управлялась тестовой обвязкой. Приёмочный прогон
на клоне вашего BitrixVM должен дополнительно проверить systemd, Битрикс,
базу данных, фоновые задания и рабочие сценарии сайта.
Результаты штатных тестов PHP, включая ожидаемые сбои и особенности старых
tzdata/OpenSSL, подробно указаны в `BUILD-INFO.txt` внутри выпуска.

## Проверка установщика rc9 с PHP 8.2

На одноразовом CentOS 7 с настоящим Apache 2.4.6 и mod_php выполнены
автоматическая настройка, обновление 8.2.20 → 8.2.35, повторный запуск,
откат при отсутствующем CLI PHP и повторный откат. Исходный набор RPM
восстановлен точно; временные файлы после проверок отсутствуют.
Проверены выбор сайтов, закрытый доступ, прерывания и подмена каталогов.
Условия, результаты и ограничения — в [VALIDATION-rc9.md](VALIDATION-rc9.md).

## Проверка установщика rc10 и PHP 8.3

На одноразовом CentOS 7 с настоящим Apache/mod_php проверены обновления
8.2.20 → 8.2.35 и 8.3.8 → 8.3.36 из подписанных комплектов, повторный запуск
без переустановки и откат при отсутствующем PHP CLI. Исходный RPM-инвентарь
восстановлен точно. Отдельно проверены все 32 основных RPM новой сборки 8.3,
закрытая веб-проба, выбор сайтов, прерывания и очистка временных файлов.

Штатный набор PHP 8.3 дал два сбоя, воспроизводимых на исходном PHP 8.3.8
(текст ошибок OpenSSL 1.0.2 и локаль Unicode-пути); остальные результаты,
ограничения сборочного журнала и дополнительные проверки раскрыты в
`BUILD-INFO.txt` выпуска. Это не утверждение, что все upstream-тесты зелёные.

Полные условия и результаты — в [VALIDATION-rc10.md](VALIDATION-rc10.md).
Контроль публичного скачивания и подписей публикуется отдельным подписанным
`HTTPS-VALIDATION.txt` в выпуске PHP 8.3. Приёмочный прогон на клоне вашего
BitrixVM остаётся обязательным.
