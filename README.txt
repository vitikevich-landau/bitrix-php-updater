BITRIX SERVER MASTER
Русскоязычный диагностический мастер и управляемое обновление PHP на старом BitrixEnv
Версия: 1.0.0-rc8 (пилотная)
Дата комплекта: 07.11.2026

БЫСТРЫЙ СТАРТ

  bash install.sh --check       # один следующий шаг
  bash install.sh --plan        # последовательность для найденного профиля
  bash install.sh --audit       # подробности и JSON-отчёт
  bash install.sh --auto-update # подготовка и установка из выпуска проекта
  bash install.sh               # меню

КТО И ЧТО ДЕЛАЕТ

1. Администратор запускает bash install.sh --check и читает следующий шаг.
2. При PHP ниже 8.2 команда bash install.sh --plan показывает маршрут.
   На клоне администратор входит под root и открывает меню окружения

     bash /root/menu.sh

   Затем выбирает указанный в плане пункт и нужный хост. Обновление
   пакетов выполняет штатная фоновая задача BitrixEnv.
3. Для перехода с 7.4 выбирайте по одному этапу
   7.4 → 8.0 → проверка сайта → 8.1 → проверка сайта → 8.2.
   С PHP 8.0 начинайте с 8.1, с PHP 8.1 — с 8.2. Для более старых
   версий следуйте отдельному маршруту из --plan.
4. После каждого этапа дождитесь успешного завершения фоновой задачи,
   проверьте доступные обновления ядра и Marketplace и работу сайта.
   Сохраните проверенное состояние перед следующим этапом.
5. На PHP 8.2.x повторите bash install.sh --check. Для 8.2.0–8.2.34
   подходящий сервер можно обновить до 8.2.35 нашим мастером.
   Для автоматической загрузки выполните настройку из раздела 6А
   и запускайте --auto-update. Владелец выпуска готовит и подписывает
   комплекты по разделу 6. На 8.2.35 целевой патч уже установлен.

Диагностические команды --check, --audit и --plan работают на чтение.
Переходы между ветками запускает администратор в меню BitrixEnv.
Автоматическую подготовку и установку запускает --auto-update.
Для ранее подготовленных локальных комплектов доступен --update.

--check сразу показывает, требуется ли действие по PHP. Это локальная
проверка без Python. Вердикт по PHP CLI, состояние RPM, проверка сайта
и поддержка ОС отображаются отдельно. Если CLI уже на целевой версии,
а RPM не подтверждены, мастер укажет причину для проверки пакетов.
В полном аудите отдельно сравниваются php, php-cli и php-common
с версией PHP CLI. Расхождения, дубли и отсутствующие пакеты выводятся
с пояснением следующего действия.
Если настроен закрытый маршрут из раздела 7, проверьте и PHP сайта:

  bash install.sh --check --url https://site.ru/_php_health.php

--audit собирает расширенный инвентарь, сверяет версию ветки с PHP.net
и сохраняет JSON-отчёт в текущую папку. Для офлайн-проверки или своего
имени файла используйте:

  bash install.sh --audit --offline --report ./audit-full.json

Если Python 3.8+ недоступен, аудит сохранит сокращённый отчёт.
Раздел 11 описывает установку отдельного Python для полного аудита.
Команда без параметров открывает меню в интерактивном терминале.
Enter открывает раздел проверок, следующий Enter запускает быстрый чек. Цвета работают в терминале, а префиксы
статусов видны и без цвета. Для отключения цветов:

  NO_COLOR=1 bash install.sh --check

1. ВАЖНО ПРОЧИТАТЬ ПЕРЕД ЗАПУСКОМ
====================================================================

Это НЕ универсальный установщик для любого сервера Linux. Полный путь
обновления реализован для конкретного профиля:

  ОС:            CentOS 7 x86_64
  Окружение:     BitrixEnv с конфигурацией /etc/httpd/bx
  PHP:           установленный пакетами RPM PHP 8.2.x
  Веб-PHP:       Apache 2.4 + prefork + mod_php
  Версия-цель:   PHP 8.2.35
  БД:            не обновляется
  Сайт Битрикс:  файлы сайта не переписываются мастером

PHP-FPM, Software Collections (php82-php-*), CentOS 8, AlmaLinux,
Rocky Linux, Debian, Ubuntu и другие ветки PHP программой НЕ ОБНОВЛЯЮТСЯ.
Диагностика этих систем доступна, установка заблокирована.

Это пилотный выпуск для прогона на клоне. Синтаксис и отдельные сценарии
проверены локально. Полный цикл сборки, установки и отката на копии
вашего BitrixEnv предстоит проверить. rpm --test проверяет пакетную
транзакцию. Работу Битрикса проверьте по разделам 7–9.

CentOS 7 уже не поддерживается. Исправление PHP НЕ решает проблем
безопасности старой ОС. Поддержка PHP 8.2 завершится 31.12.2026.
Рекомендуется планировать миграцию на поддерживаемое окружение.

2. КАКИЕ ФАЙЛЫ НУЖНЫ
====================================================================

  install.sh    — один автономный Bash-файл, содержит Python-диагност.
  README.txt    — эта инструкция.

В архиве ZIP те же файлы. Для работы самого мастера достаточно
одного install.sh. Интернет может понадобиться для источников PHP,
проверки обновлений или отдельного Python.

Скопируйте install.sh на сервер, например в /root/bitrix-master/
по SSH/SFTP, затем:

  cd /root/bitrix-master
  chmod 700 install.sh
  bash install.sh --help

Не нужно запускать «curl ... | bash» из интернета: сначала изучите
файл, его происхождение и контрольную сумму.

3. БЫСТРАЯ ДИАГНОСТИКА — БЕЗ ИЗМЕНЕНИЙ СИСТЕМЫ
====================================================================

  bash install.sh --diagnose
  bash install.sh -d --quick
  bash install.sh --diagnose --full
  bash install.sh --diagnose --full --check-updates
  bash install.sh --diagnose --offline

Печать JSON на экран:

  bash install.sh --diagnose --json

Сохранение JSON-отчёта в текущую папку:

  bash install.sh --diagnose --full --report

Сохранение под заданным именем:

  bash install.sh --diagnose --full --report ./audit-before.json

Сравнение до/после (один и тот же hostname):

  bash install.sh --compare audit-before.json audit-after.json

При --diagnose программа НЕ устанавливает пакеты, НЕ ставит Python,
НЕ перезапускает Apache/Nginx, НЕ редактирует конфигурации.
Если не задан --report, отчёт на диск не записывается.

Внимание: необязательная проверка --url выполняет HTTP HEAD-запрос
и может оставить запись в access.log сайта:

  bash install.sh -d --url https://example.org/

Проверка --check-updates обращается к php.net по HTTPS.
Режим --offline запрещает такие сетевые проверки.

Если совместимого Python 3.8+ на сервере нет, запускается ограниченная
диагностика на чистом Bash. Она также ничего не устанавливает.

4. МЕНЮ НА РУССКОМ
====================================================================

Для интерактивного меню в SSH:

  bash install.sh

Главное меню
  1. Проверки и диагностика
  2. Подготовка и обновление PHP
  3. Откат и состояние операции
  4. Справка по командам
  0. Выход

В проверках доступны быстрый чек, план, офлайн/онлайн аудит,
проверка веб-PHP, подробный экран и установка отдельного Python.
В обновлении доступны план, автоматическое обновление, первичная
настройка, сборка на клоне, ручная установка и подпись выпуска.
Внутри разделов пункт 0 возвращает назад. Пустые обязательные
поля установки, отката и подписи отменяют выбранное действие.

Прерывать работу можно Ctrl+C, но НЕ делайте этого во время rpm -Uvh:
незавершённая пакетная транзакция требует отдельной проверки.

5. ПОСМОТР ПЛАНА ОБНОВЛЕНИЯ (БЕЗ УСТАНОВКИ)
====================================================================

  bash install.sh --plan

Команда показывает маршрут по установленному PHP и найденному выпуску
BitrixEnv. На PHP ниже 8.2 шаги описывают подготовку на клоне. После
перехода на 8.2.x повторите --check. Мастер предлагает свой патч до
8.2.35 после проверки поддерживаемого профиля. Если нужен переход
или профиль заблокирован, --plan возвращает ненулевой код.

План показывает, какие варианты документированы. Доступность архивов,
разрешение зависимостей RPM и совместимость сайта подтверждаются
отдельно на клоне. План работает на чтение и печатает инструкции
для администратора. Для инвентаря используйте --audit --offline.

Перед обновлением обязательно:
  - сделать актуальный и проверенный снимок виртуальной машины;
  - убедиться, что доступна консоль гипервизора, а не только SSH;
  - согласовать окно обслуживания сайта;
  - проверить свободное место и доступ к источникам пакетов;
  - иметь план восстановления старой версии PHP.

Снимок ВМ должен быть создан средствами гипервизора/резервного ПО:
мастер НЕ умеет создавать или проверять VMware-снимок самостоятельно.

6. СБОРКА И ПОДПИСЬ КОМПЛЕКТОВ RPM
====================================================================

Клонируйте ВМ, изолируйте её от посетителей и отключите на ней рассылки
и внешние интеграции. Команда для отдельной сборочной ВМ приведена ниже.

  bash install.sh --build --builder

Мастер проверяет профиль и SHA-256 всего Remi SRPM, затем SHA-256 и
GPG-подпись архива PHP внутри SRPM. Он адаптирует spec под ICU 73
и добавляет патч совместимости с OpenSSL 1.0.2. Сборка оставляет RPM
и SHA256SUMS в каталоге, указанном в журнале. Установка build-зависимостей
на клоне может обновить системные пакеты. Прочитайте предложенную
транзакцию yum-builddep перед подтверждением.

Для локального исходного пакета используется тот же закреплённый хеш.

  bash install.sh --build --builder --srpm /root/php-8.2.35-1.remi.src.rpm

Источник SRPM:
  https://rpms.remirepo.net/SRPMS/php-8.2.35-1.remi.src.rpm

Подготовьте два отдельных каталога. Первый содержит новые RPM.
Второй содержит точные оригинальные RPM каждого установленного
основного пакета PHP. Сверьте имя, epoch, версию, release и архитектуру
с установленными пакетами.

  rpm -qa --qf '%{NAME}|%{EPOCH}|%{VERSION}|%{RELEASE}|%{ARCH}\n' \
      | grep -E '^php(\||-)'

Проверьте кэш yum, архив вашего репозитория и предыдущие дистрибутивы.
Если исходный RPM отсутствует, возьмите его из доверенного источника.
Список установленных пакетов сам по себе не содержит их файлов RPM.
Для стандартного php-zipstream мастер проверяет архитектуру, файлы
и зависимости по RPM. У этой библиотеки свой выпуск, поэтому её
версия не входит в сравнение основных пакетов PHP.
Для старых и новых наборов проверьте происхождение пакетов до подписи.

На доверенной машине подпишите оба манифеста одним доверенным ключом. Для штатного GnuPG на CentOS 7 используйте ключ подписи RSA.
Задайте SIGNER_FPR полным отпечатком вашего ключа и подставьте свои пути.

  for rpm_dir in /path/NEW_RPMS /path/OLD_RPMS; do
      (
          cd "$rpm_dir" &&
          sha256sum -- ./*.rpm > SHA256SUMS &&
          gpg --armor --digest-algo SHA256 --local-user "$SIGNER_FPR" \
              --detach-sign --output SHA256SUMS.asc SHA256SUMS
      ) || break
  done
  gpg --export "$SIGNER_FPR" > rpm-signing.gpg

При пересоздании комплекта уберите старую SHA256SUMS.asc до подписи
и убедитесь, что обе подписи созданы. В каждом из двух каталогов
должны остаться только RPM, SHA256SUMS и SHA256SUMS.asc. Передайте только публичный keyring
rpm-signing.gpg отдельно по доверенному каналу, сверьте отпечаток
и положите его в каталог root, например /root. Файл и все каталоги
в его пути должны принадлежать root без права записи для группы
и остальных. Приватный ключ остаётся на машине подписи. На целевой ВМ нужен gpgv.

====================================================================
6А. АВТОМАТИЧЕСКАЯ ЗАГРУЗКА И УСТАНОВКА ИЗ GITHUB RELEASES
====================================================================

Владелец проекта один раз собирает новые RPM и пополняет архив точных
прежних пакетов. На доверенной машине подписи выполните

  bash install.sh --prepare-release \
      --new-rpm-dir /path/NEW_RPMS --old-rpm-dir /path/OLD_RPMS \
      --signer FULL_RSA_FINGERPRINT --output /path/NEW_RELEASE

Каталог NEW_RELEASE должен быть новым. В нём будут готовые RPM,
NEW-SHA256SUMS, OLD-SHA256SUMS, обе .asc-подписи и release-keyring.gpg.
Старые RPM переименованы по хешу точной записи NEVRA для адресного
скачивания. Входные RPM должны происходить из доверенных источников.
Команда подписи подтверждает доверие владельца входным пакетам.

Размещайте эти файлы в GitHub Releases. Закрытый ключ храните на
доверенной машине подписи. Публичный ключ проекта размещён в репозитории,
его SHA-256 закреплён в install.sh.

На клиентском сервере после перехода на PHP 8.2.x подготовьте закрытый
веб-тест по разделу 7 и один раз выполните от root

  bash install.sh --setup-update

Мастер спросит URL, проверит исходный веб-PHP, получит закреплённый
публичный ключ и сохранит настройки в /etc/bitrix-php-update.conf.
Затем используйте одну команду или соответствующий пункт меню

  bash install.sh --auto-update

В первом выпуске архив прежних RPM содержит PHP 8.2.20-1.el7.remi,
x86_64, без epoch. Для иных исходных сборок 8.2.x требуется пополнить
архив их точными оригинальными пакетами. Проверяется весь установленный
набор основных PHP RPM, а не только строка версии CLI.

Мастер проверит профиль и текущие RPM, подписи двух каталогов,
получит точные прежние и новые пакеты, подтвердит состав, проверит
транзакцию и сайт, затем выполнит обычный сценарий установки.
Подтверждения снимка и самой установки остаются частью запуска.
Если точного старого RPM нет в подписанном архиве, подготовка завершится
с указанием недостающей NEVRA до установки пакетов. Владелец выпуска
может добавить оригинальный RPM и повторно подписать каталог.

В комплект входят пакеты PHP. Недостающие системные библиотеки не
скачиваются и не устанавливаются: rpm --test перечислит неудовлетворённые
зависимости и остановит обновление до изменения пакетов. Репозитории
и остальные пакеты ОС автоматическая команда не меняет.

Для задания после проверки актуального снимка

  bash install.sh --auto-update --unattended --backup-verified

При отдельной конфигурации

  bash install.sh --auto-update --config /root/client-update.conf

Конфигурация содержит ровно по одной строке для каждого поля

  SOURCE=https://github.com/vitikevich-landau/bitrix-php82-updater/releases/download/php-8.2.35-el7-r1
  KEYRING=/root/release-keyring.gpg
  HEALTH_URL=https://example.org/_php_health.php

Это значения без кавычек и shell-команд. SOURCE также допускает
абсолютный путь к локальному каталогу выпуска. Конфигурация, keyring
и каталоги в их путях должны принадлежать root без записи для группы
и остальных. Для файла конфигурации используйте права 0600.

В подписанном каталоге могут быть RPM для других клиентских серверов.
Мастер загружает точные старые RPM текущего узла. Перед установкой
проверяется полнота требуемого набора, подпись полного каталога,
метаданные и хеш каждого выбранного файла.
Повторный запуск после ошибки загрузки заново проверяет комплект.

====================================================================
7. ПОДГОТОВКА ВЕБ-ПРОВЕРКИ И ОБНОВЛЕНИЕ
====================================================================

Выберите маршрут на том же виртуальном хосте, который обслуживает
Битрикс. Ограничьте его входным прокси или веб-сервером для локальных
запросов и отключите кэширование. Проверьте извне, что маршрут закрыт.
Если запрос проходит через nginx, убедитесь, что маршрут реально
передаётся в тот Apache, который обслуживает сайт.

Пример содержимого закрытого _php_health.php.

  <?php
  header('Content-Type: text/plain; charset=UTF-8');
  header('Cache-Control: private, no-store');
  if (PHP_SAPI !== 'apache2handler' || !function_exists('mb_substr')
      || !extension_loaded('mysqli')) {
      http_response_code(503);
      exit;
  }
  echo 'BITRIX_MASTER_OK ' . PHP_VERSION . " apache2handler\n";

Подберите проверяемые расширения под свой сайт. Для проверки
инициализации Битрикса и БД используйте отдельный согласованный
сценарий сайта. Этот короткий пример проверяет веб-PHP и два
расширения. Мастер сам не создаёт и не публикует PHP-файлы.

Используйте HTTP(S) URL с путём, без логина, пароля, параметров и
фрагмента. Явный порт допустим. Мастер закрепляет домен и порт за
127.0.0.1, отключает прокси и проверяет HTTPS-сертификат. Маршрут
должен вернуть HTTP 200 и единственную строку с ожидаемой версией
веб-PHP и SAPI apache2handler. Редирект, статическая главная страница
и ответ другого узла проверку не пройдут.

Перед установкой сделайте проверенную резервную копию, откройте
доступ к консоли гипервизора, запланируйте окно обслуживания и
приостановите сторонние пакетные операции. Запустите от root.

  bash install.sh --update --rpm-dir /root/NEW_RPMS \
       --rollback-dir /root/OLD_RPMS --rpm-keyring /root/rpm-signing.gpg \
       --url https://example.org/_php_health.php

Если --rpm-dir опущен, мастер проверит стандартные каталоги сборки.
В обычном режиме мастер запрашивает подтверждения в терминале.
Запишите ID сессии
из вывода. Мастер сохраняет проверенные комплекты, точный список RPM,
конфигурации и исходный список расширений PHP. Затем он проверяет
веб-PHP до установки, проверяет, что пакеты не затрагивают сторонние
RPM через Obsoletes, тестирует транзакцию и устанавливает пакеты.
Перед полным перезапуском мастер проверяет конфигурацию Apache.
После запуска проверяет версии CLI и веб-PHP, расширения и службу.

При ошибке смотрите состояние сессии и журнал. Пакеты могли уже
измениться. Для восстановления используйте ту же сессию из раздела 9.
Если 8.2.35 уже установлен, мастер выполняет проверку работоспособности.
Успешная веб-проверка подтверждает только проверенный маршрут.

Для запуска из задания после проверки бэкапа, подписанных комплектов
и закрытого маршрута используйте оба параметра:

  bash install.sh --update --rpm-dir /root/NEW_RPMS \
       --rollback-dir /root/OLD_RPMS --rpm-keyring /root/rpm-signing.gpg \
       --url https://example.org/_php_health.php \
       --unattended --backup-verified

--backup-verified передаёт ваше подтверждение, что бэкап или снимок
уже проверен. --unattended выполняет операцию без ожидания ввода.
В этом режиме мастер так же проверяет подписи, RPM-транзакцию и сайт.
При отказе ориентируйтесь на код завершения, --status и журнал.

====================================================================
8. ПРОГОН НА КЛОНЕ
====================================================================

1) Снимите исходный отчёт и проверьте профиль.

   bash install.sh --diagnose --full --offline --report ./audit-before.json
   bash install.sh --plan

2) Соберите и подпишите новые RPM, подготовьте точные старые RPM,
   проверьте закрытый маршрут с исходной версией PHP.
3) Запустите обновление из раздела 7. Проверьте логин в админку, формы,
   подключение к БД, фоновые задачи и нужные интеграции. Снимите второй
   отчёт и сравните его с первым.

   bash install.sh --diagnose --full --offline --report ./audit-after.json
   bash install.sh --compare ./audit-before.json ./audit-after.json

4) Выполните откат по ID и проверьте исходные версии и работу сайта.
5) На одноразовом клоне проверьте отказ веб-маршрута с HTTP 500 при
   активном Apache. Проверьте, что мастер сообщает о сбое и что
   восстановление проверяет веб-PHP. Отдельно отработайте неудачный
   запуск Apache и частичное изменение набора RPM.

====================================================================
9. ОТКАТ ПО ID СЕССИИ
====================================================================

Откат использует подписанные старые RPM и исходный список пакетов,
которые мастер сохранил перед установкой. Используйте ID исходного
обновления, даже если последняя операция была попыткой отката.

  bash install.sh --rollback --session YYYYMMDDTHHMMSSZ-PID

Для явно выбранной сессии откат также доступен из задания:

  bash install.sh --rollback --session YYYYMMDDTHHMMSSZ-PID --unattended

Если маршрут проверки переехал, можно указать --url с новым закрытым
адресом на этом же узле. Мастер проверяет, что текущий комплект относится
к этому обновлению, восстанавливает отсутствующие и изменённые RPM,
перезапускает Apache и проверяет точные версии и веб-PHP. Если исходная
установка или предыдущий откат прервались внутри RPM-транзакции,
мастер переустанавливает весь сохранённый набор. Записи в базе RPM
могут уже показывать прежние версии при незавершённом восстановлении
файлов. Повторите ту же команду с ID исходного обновления.
После подтверждённого восстановления RPM повторный запуск продолжит
проверку Apache и сайта. Ошибки послепроверки приводят к ненулевому
коду завершения. Сессия попытки
отката хранится отдельно, с указанием исходной сессии.

Откат пакетов не восстанавливает базу и содержимое сайта. Архив
configuration.tar.gz можно использовать для ручного восстановления
нужных настроек. Если после установки появились .rpmnew/.rpmsave,
сверьте их с рабочими файлами. Для установок, сделанных вручную или
старой версией мастера, используйте проверенный снимок или отдельную
процедуру восстановления из точного старого комплекта RPM.

====================================================================
10. ЛОГИ, СОСТОЯНИЕ И КОНТРОЛЬ
====================================================================

В режиме root журналы находятся в:

  /var/log/bitrix-server-master/

Данные о сессиях:

  /var/lib/bitrix-server-master/sessions/

Рабочая директория для сборки:

  /var/lib/bitrix-server-master/work/

Последняя сессия:

  bash install.sh --status

Права каталогов ограничены. В журналах МОГУТ оказаться
конфигурационные сведения, поэтому не размещайте их публично.

После прерывания проверьте состояние сессии и журнал. Мастер сохраняет
исходный набор RPM и идентификатор сессии до пакетной транзакции.
Проверяйте rpm -qa, php -v, php -m, httpd -t и systemctl status httpd.
Для возврата используйте ID исходного обновления. Сохраняйте каталоги
сессий до завершения окна обслуживания и проверки восстановления.

Пример ручных контрольных команд:

  php -v
  php -m
  httpd -t
  httpd -M | grep php
  systemctl is-active httpd
  tail -n 40 /var/log/httpd/error_log

Полезно повторить после обновления диагностику с --report и
сравнить с отчётом ДО работ через --compare.

====================================================================
11. PYTHON: ЕСЛИ ЕГО НЕТ
====================================================================

Подробный диагностический модуль написан на Python 3.8+ (стандартная
библиотека). Само обновление управляется Bash и не требует Python.
Это сделано специально, чтобы старый системный Python 2.7 и yum
оставались нетронутыми.

Если Python 3 отсутствует, доступна ограниченная Bash-диагностика.
Для отдельной расширенной диагностики можно поставить изолированный
Python в /opt/bitrix-server-master (для root) по команде:

  bash install.sh --bootstrap-python

Мастер покажет URL, контрольную сумму и запросит подтверждение.
Системный /usr/bin/python не меняется. Если архив не подходит для
старой glibc или контрольная сумма не совпадает, установка прекратится.
Это НЕ установка через yum, сторонние системные пакеты не обновляются.

Если сервер не имеет выхода на GitHub, поддерживается локальный
архив с ожидаемой контрольной суммой:

  bash install.sh --bootstrap-python --python-archive /root/python.tar.gz

Этот опциональный bootstrap в пилотной версии требует отдельного
тестирования на разных типах CentOS 7.

====================================================================
12. ЧТО МАСТЕР НЕ ДЕЛАЕТ
====================================================================

  - Не обновляет ОС CentOS и MySQL/Percona.
  - Не мигрирует сайт на новую ВМ.
  - Не меняет размер диска автоматически.
  - Не исправляет MaxRequestWorkers и производительность Apache.
  - Не устанавливает PHP-FPM или параллельную ветку PHP.
  - Не гарантирует сохранение всех сторонних расширений PHP.
  - Не обещает 100% исправность сайта по одному коду HTTP 200.
  - Не умеет создавать снимки VMware/Hyper-V/KVM самостоятельно.
  - Не продолжает опасную RPM-транзакцию автоматически после сбоя.
  - Не заменяет проверку происхождения RPM перед их подписью.
  - Не выбирает версии ядра, модулей или БД для перехода на другую ветку PHP.

13. МАРШРУТЫ ДЛЯ СТАРОГО PHP И ИСТОЧНИКИ
====================================================================

BitrixEnv, ядро Битрикса и PHP проверяются отдельно. Полный аудит
показывает выпуск RPM окружения и сайты в стандартных каталогах.
Версии ядра и модулей читаются из файлов. Подтвердите веб-PHP через
закрытый маршрут и проверьте админку, формы и интеграции на клоне.

  - BitrixEnv 7.5.3–7.5.5 на CentOS 7: переход на 8.2 предусмотрен.
    Для 7.5.3 с PHP 8.1 сначала проверьте обновление окружения
    до 7.5.4 или 7.5.5 на клоне. В 7.5.4 исправили пункт Upgrade PHP.
    В меню выберите один хост в Manage servers in the pool →
    8. Update PHP and MySQL → Upgrade PHP и ближайшую нужную ветку.
    Для 7.4 сначала выберите 8.0, для 8.0 — 8.1, для 8.1 — 8.2.
    В меню CRM пункт обновления PHP может быть под номером 6.
    Сверяйте название. Проверьте комплект RPM и зависимости каждого
    этапа. После каждой задачи проверяйте сайт и делайте снимок
    проверенного состояния перед следующим повышением.
    В 7.5.5 выбор сразу 8.2 может запустить все промежуточные ветки
    одной задачей. Для проверки сайта между этапами выбирайте
    следующую ветку отдельным запуском.
  - Более ранний BitrixEnv 7: сначала проверьте, можно ли обновить
    окружение на этой ОС по инструкции для найденного выпуска.
    Для перехода на 7.5.0 было отдельное примечание по Ansible.
    После обновления окружения повторите --check и --plan.
  - Перед переходом на PHP 8.2 на клоне установите доступные
    обновления ядра, модулей и решений Маркетплейса. Проверьте
    пользовательский код, кодировку и расширения. После каждого
    перехода снова проверьте доступные обновления ядра и Marketplace.
    Для PHP 5.x и ранних 7.x промежуточную ветку выбирайте по
    совместимости сайта.
  - CentOS 6, неподходящая ОС или недоступные зависимости:
    подготовьте перенос сайта на поддерживаемое окружение.
  - PHP 8.2.0–8.2.34: для подходящего профиля используйте шаги
    установки 8.2.35 и отката из разделов 6–9.
  - PHP 8.2.35 и выше: --check покажет, что целевой патч не требуется.

Запущенную задачу отслеживайте в Background pool tasks →
View running tasks. В стандартном меню v7 это 10 → 1.
Логи задач находятся в /opt/webdir/temp. Дождитесь окончания и
проверьте результат в журнале, затем проверяйте сайт и продолжайте.
После обновления окружения или PHP выполните на клоне предусмотренную
инструкцией перезагрузку и повторную проверку сайта. Для рабочего
сервера перезагрузку включите в согласованное окно обслуживания.

Возврат после штатного переключения ветки в меню BitrixEnv проверяйте
восстановлением снимка клона. Откат по ID относится к установке 8.2.35
этим мастером из подписанного комплекта RPM.
